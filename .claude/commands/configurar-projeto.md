argument-hint: "<nome do projeto> [objetivo em uma frase]"

Projeto: $ARGUMENTS

Ambientes (não negociável): **local** usa a branch `dev` do Neon e a instância de desenvolvimento do Clerk; **preview** usa uma branch do Neon por preview (integração Neon ↔ Vercel) e a instância de desenvolvimento do Clerk; **produção** usa a branch `main` do Neon e a instância de produção do Clerk, e só o deploy mexe nela (migrações no build da API). A URL de produção nunca entra no `.env` local nem no ambiente Preview.

0. **Tipo e nível de movimento** (pergunte se não estiver claro): sistema completo (padrão) ou site institucional (remova `apps/web/app/dashboard`, `apps/web/app/admin`, `apps/web/app/billing` e os cards do painel; a API pode ficar só com contato). Registre no `CLAUDE.md` do projeto se o front é estático, animado ou 3D (animado/3D: agente `motion` + skill `motion-kit`).
1. **Identidade**: `name` no `package.json` da raiz, `apps/web/lib/site.ts` (nome, descrição, dados da empresa das páginas legais) e o título do `README.md`.
2. **Neon** (agente `infra`; confirme antes de criar recursos): projeto em `aws-sa-east-1`; a branch `main` é a produção. Crie a branch `dev` e use a connection string *pooled* dela em `DATABASE_URL` do `.env` local; anote o host da `main` sem `-pooler` em `PRODUCTION_DATABASE_HOST`. Rode `npm run db:migrate` (vai para a `dev`).
3. **Clerk**: duas instâncias (desenvolvimento para local/preview, produção com domínio próprio). Provedores de login; Sessions > Customize session token `{ "metadata": "{{user.public_metadata}}" }` (papéis do `/admin`); webhook `<API>/webhooks/clerk` (`user.created`, `user.updated`, `user.deleted`) com o secret em `CLERK_WEBHOOK_SIGNING_SECRET`; Attack protection ligado; copie a "JWT public key" para `CLERK_JWT_KEY` (verificação sem rede). Reverificação (excluir conta, trocar papel) já vem pronta.
4. **Variáveis locais**: copie os `.env.example` para `.env` em `apps/api` e `apps/web` e peça ao usuário para colar as chaves (nunca no chat). Obrigatórias: Neon (branch `dev`), Clerk, R2, `CORS_ORIGINS`, `APP_URL`. No web, `API_URL=http://localhost:3000` (o navegador chama `/api`, que o Next repassa). Opcionais: Stripe (`STRIPE_PRICE_IDS` obrigatório em produção; `BILLING_OWNER=user|org`), Resend, Ably, Upstash Redis/QStash, Sentry, PostHog e `FEATURE_FLAGS`, `CONTACT_EMAIL`, `NEXT_PUBLIC_SITE_URL`.
5. **Validar**: `npm install`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; `npm run dev` e abra `http://localhost:3000/health` e `http://localhost:5173`.
6. **Vercel** (agente `infra`): dois projetos (`apps/web` e `apps/api`, região `gru1` já fixada nos `vercel.json`; a API builda com `npm run vercel-build`, que aplica as migrações e falha o deploy se a migração falhar).
   - Instale a integração **Neon ↔ Vercel** no projeto da API: Production aponta para a branch `main`; Preview cria uma branch por deploy (injeta `DATABASE_URL`/`DATABASE_URL_UNPOOLED`). Defina `PRODUCTION_DATABASE_HOST` em todos os ambientes e `MIGRATE_PREVIEW=true` no Preview.
   - Web: `API_URL` por ambiente (Production = URL da API; Preview = `https://<projeto-api>-git-{branch}-<time>.vercel.app`), `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `R2_UPLOAD_ORIGIN` (CSP), `API_PROXY_SECRET` (mesmo valor da API). Chaves do Clerk de desenvolvimento no Preview e de produção na Production. Sem `API_URL` o build do web falha na Vercel (de propósito).
   - `{branch}` exige que a API seja buildada em toda branch: no projeto da API desligue "Skip deployments when there are no changes to the root directory"/"Skip unaffected projects" e não use Ignored Build Step que pule branches; se quiser manter o skip, use no Preview um `API_URL` fixo de staging.
   - API: `APP_URL`, `API_PROXY_SECRET` (mesmo do web; IP real do visitante no rate limit), `CORS_ORIGINS` (URL do front, sem `*`), `AUTHORIZED_PARTY_PATTERN` (regex das URLs de preview do web, ex. `^https://<projeto-web>-[a-z0-9-]+-<time>\.vercel\.app$`), `API_PUBLIC_URL`, `CRON_SECRET` (Vercel Cron da retenção), `TURNSTILE_SECRET_KEY`, Upstash Redis (ou `RATE_LIMIT_DISABLED=true` consciente).
   - Domínio, CORS do bucket R2 (PUT/GET) para o domínio do front e para os previews.
7. **Turnstile**: Cloudflare > Turnstile > widget com o domínio (e `vercel.app` para previews); site key no web, secret na API (`TURNSTILE_ALLOWED_HOSTNAMES` se houver mais de um domínio).
8. **GitHub**: environment `production` com `DATABASE_URL_UNPOOLED` (backup e migração manual de emergência) e os opcionais do backup (`R2_ACCOUNT_ID`, `R2_BACKUP_*`); secrets de repositório `E2E_CLERK_PUBLISHABLE_KEY`/`E2E_CLERK_SECRET_KEY` (instância de desenvolvimento) e `VERCEL_AUTOMATION_BYPASS_SECRET` para o E2E logado nos previews.
9. **Primeiro admin**: no Clerk, defina `publicMetadata` `{ "role": "admin" }` no seu usuário; depois o `/admin` gerencia os demais.
10. **Relatório**: o que foi feito, o que falta o usuário fazer e o próximo passo: `/planejar` com o briefing.
